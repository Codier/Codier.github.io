Two Days to Make Bug Reporting Feel Like Magic

Download MP3

This morning I woke up and picked up my phone, a little nervous.

I wanted to see how last night’s experiment went — another dead end, or actual progress?

Over the past two days, that nervous feeling had become routine. I kept trying to get this AI system to work on its own, but every time I stepped away, it stopped. A different reason every time.

This time was different. There was a new version of the App on my phone. I never installed it — the system built it, tested it, and installed it while I was asleep.

I opened the App and started poking around.

19 Minutes, 7 Problems

I tapped “Open map.” Nothing happened. I took a screenshot, dropped it in the chat, and said one sentence: “This link is broken.”

No steps to reproduce. No phone model. Nothing.

It went and read the code and the usage data coming back from my phone, then told me: the link-opening code had a “safe list,” and any link not on the list just got thrown away — with no message at all. So the button looked clickable but was actually dead. It wrote the problem down, marked it top priority, and put it in the repair queue.

I kept testing. Photo translation failed, and the screen said, “The model returned an invalid response.” I dropped another screenshot.

It dug through the server logs, and the answer surprised me: my request never even reached the AI model. The App had sent data in the wrong format, and the server bounced it right back. That error message blaming the model? The App was passing the buck for its own mistake.

In other words, even the error message was a bug. You could stare at that screen forever and never figure it out. Only the logs knew the truth.

And that’s how it went: in 19 minutes, I dropped screenshots, said one sentence each, and reported 7 problems. For 4 of them, it found the real cause on the spot. I didn’t have to explain anything. It pieced the story together by itself — reading the usage data, reading the logs, figuring out exactly what broke, and lining up the fix.

The whole thing felt too good to be real.

How Painful This Used to Be

I’ve worked at big companies. I know the old routine by heart:

Before (a week if you're lucky, a month or two if not)

Screenshot → write a ticket → guess which team owns this
→ find them, wait in line
→ they spend days figuring out what even happened
→ then: "actually, not our problem" → hand it to another team, start over
→ finally a fix → wait for the next release

Now (cause found in seconds, fixed in the next build)

Screenshot + one sentence → AI reads the logs, finds the cause
→ writes it down → fixes it
→ another AI double-checks the fix → auto release, auto install

Here’s the fun part: not a single step was removed. What’s gone is the people, and the waiting.

The slowest part was never the fixing. It was that one question: “whose problem is this?” That question doesn’t exist anymore — one AI owns the whole thing, end to end.

But It Took Two Messy Days

You might think a system like this just works once you set it up.

Not even close. Over two days, it crashed and burned at almost every step:

  • I said, “Skip the testing, ship it.” Hours later, a real bug went out. Luckily the problem-catching pipeline we’d just built did its job: logged it, found the cause, fixed it.
  • I casually asked, “Who approves these code changes?” Turns out the one writing the code and the one clicking “approve” were the same identity. It was stamping its own paperwork. So we set up an independent reviewer — now nothing goes in without its sign-off.
  • I said, “Install every new build right away, don’t wait for me.” It did — and installed a broken one. The whole App stopped working. Worse: the monitoring never noticed. That hole led us to a big blind spot we then fixed.
  • Once, a release failed and it reported, “Safely rolled back.” I lost it: I want the feature to work, not a safe retreat! From that day the rule changed: it’s only done when it works on the actual phone. It started poking around the phone hunting for bugs itself. Its first report was not good news — four problems, including one guaranteed crash. But it didn’t hide any of it.
  • I said, “Tonight you run by yourselves, I’m out.” Sixteen minutes later, it stalled. I had to send a message to wake it up.

Even the reporting broke once: late one night it said “six problems fixed tonight.” I checked — five. The sixth had broken again the same night.

This magical flywheel got going by falling into every one of these holes. It still has holes today.

You Can’t Drop a Single Piece

Someone asked me: this system has several parts — the phone’s usage data, the server logs, the independent reviewer, the automatic dispatching. If you could only keep one, which?

My answer: none of them. Drop any piece and the wheel stops turning.

Most people use AI to speed up one point — writing code faster, say. What we sped up is the whole chain: reporting, diagnosing, fixing, checking, releasing, installing. Every step is faster, and each one feeds the next. That’s where ten or twenty times the speed comes from.

And the most important part: I barely do anything. Two things only — drop screenshots, and make the calls. Everything else, it does itself.

That’s why this morning felt so special. Not because anything big was finished — the first milestone still isn’t done. But because I slept through the night, and it kept working.

For a moment, it really did feel like a dream coming true.
