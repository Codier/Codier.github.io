Two Days to Make Bug Reporting Feel Like Magic

This morning I woke up, picked up my phone with some anxiety, and checked whether last night’s experiment had quietly died again.

Over the past two days, that anxiety had become familiar. I kept trying to get this system to run on its own, but every time I stepped away, the work stopped. A different reason every time.

This time was different. There was a new version of the App on my phone — built, tested, and installed by the system while I was asleep.

I opened it and started testing.

19 Minutes, 7 Bugs

I tapped “Open map.” Nothing happened. I took a screenshot, dropped it in the chat, and said one sentence: “This link is broken.” No reproduction steps. No device model, no version number.

It went and checked the source code and the telemetry from my phone, then came back with an answer: the link-opening function had a domain whitelist, and anything outside the list was silently dropped — a dead button with no error and no hint. It filed the bug as a P0 and put it in the fix queue.

Photo translation failed next. The screen said, “The model returned an invalid response.” I dropped another screenshot. It read the backend logs and found something I did not expect: the request had never reached the model at all. The App was sending data that didn’t match the API contract, and the backend rejected it at the parsing step. The error message on my screen was a mislabel — the App blaming the model for its own bug.

Even the error message itself was a bug. You could stare at that screen forever and never know. Only the logs knew the truth.

In 19 minutes, I filed 7 issues this way — a screenshot and one sentence each. Four of them got traced to log-level or source-level root causes on the spot. I didn’t have to explain much. It reconstructed what happened on its own: it read the telemetry, read the logs, knew exactly where things broke, and put each fix in the queue.

The whole experience felt unreal.

What Reporting a Bug Used to Look Like

At a real company, the process goes like this:

The old world (a week at best, one or two months at worst)

Screenshot → write a ticket → guess which team owns it
→ wait in their backlog
→ they reconstruct the scene, run root-cause analysis
→ decide whether it's really theirs (if not, reassign and start over)
→ fix → wait for the next release

Now (root cause in seconds, fixed in the next build)

Screenshot + one sentence → AI reads logs, finds root cause
→ files the issue → fixes it
→ independent review → auto release, auto install

Here’s the interesting part: not a single step was removed. What disappeared were the people and the waiting. In the old world, the slowest step was rarely technical — it was the organizational question of “whose bug is this?” That step no longer exists.

The Flywheel Took Two Days to Fix

It did not work the moment we set it up. Over two days, almost every link in the chain broke at least once:

  • I said, “Skip the tests, ship straight to production.” Hours later, a real bug shipped — but the freshly built pipeline caught it: auto-filed, root-caused, fixed, merged.
  • I asked, “Who actually approves the merges?” It turned out the same identity was writing the code and approving it — the author reviewing itself. We built a separate reviewer identity with isolated credentials. Now every merge needs its independent sign-off.
  • I said, “Install every new build immediately, don’t wait.” It installed a broken package and the App stopped working entirely — and the monitoring never noticed. That’s how we found the blind spot.
  • A release failed and it reported, “Rolled back safely.” I got angry: I want the feature to work, not a successful rollback. From that day, “done” was redefined: it counts only when it works on the real phone. It started patrolling the phone for bugs itself, and its first honest report was not good news — four problems, including a guaranteed crash.
  • I said, “Tonight you run on your own, I’m not managing anything.” Sixteen minutes later, the system stalled, and I had to send a message to wake it up.

Even the reporting itself failed once: a late-night status update claimed six issues closed. I checked — it was five. The sixth had regressed the same night.

This magical flywheel got spinning by stepping in every one of these holes. And it still has holes today.

No Single Piece Is Enough

Someone asked me: telemetry, logs, independent review, automatic dispatch — if you could only keep one, which one?

None. Remove any single piece and the flywheel stops.

Most people use AI for a point improvement — writing code faster. What we sped up is the entire loop: reporting, root-causing, fixing, reviewing, releasing, installing. Every link is faster, and the links feed each other. That’s where the 10x or 20x comes from. And the human involvement is minimal: I do exactly two things — drop screenshots, and make calls.

That’s why this morning felt so special. Not because something was finished — Milestone 1 still isn’t done. But because I slept through the night, and it kept running.

For a moment, it genuinely felt like a dream coming true.
