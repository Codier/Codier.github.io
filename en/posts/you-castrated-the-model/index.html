You Castrated the Model. One Blunt Comment Reversed Our Architecture

Three seemingly unrelated bugs made me realize that we had written too many rules that were making decisions the AI could already make. That same day, we stopped patching, approved a new architectural direction, and reorganized the work around it.

That day, I was testing an AI app I had been building on my phone. The more I tested it, the more wrong it felt.

I asked for nearby restaurants. It returned an error. I asked about recently released movies. It said it had no live information, then confidently labeled the answer “high confidence.” I asked about the weather. It failed to work out which city I was in, quietly substituted a different guessed city, and still called the answer “high confidence.”

The three problems looked unrelated. The obvious fixes did too:

  • Add another rule to recognize movie questions.
  • Add another way to parse locations.
  • Add another restriction on the “high confidence” label.

More code. More holes patched.

Then it occurred to me that the direction itself might be wrong.

I use another AI assistant every day. It often works out for itself whether it needs to search or ask me for my location first. I never wrote a separate set of rules telling it, “When you see this word, take this route.”

I compared the two and told the AI working on my app: You built a lot of code that castrated the model. You blocked it from doing things it already knew how to do. That defeats the whole purpose of building this product.

I added one instruction: Do not change anything yet, and do not agree with me just to be agreeable. If I am wrong, push back.

It said I was about 80% right

The AI went back and audited the design. It did not surrender completely, and it did not get defensive.

It said I was about 80% right. The other 20% was that my other assistant was not a “bare model.” In fact, it had more tooling, permissions, and safety machinery behind it.

The difference was not whether a harness existed. It was where the harness stood.

Before: Code guesses what I mean → picks a route for the AI → AI handles what remains
New direction: AI understands first → answers, asks, or looks things up → code guards the boundaries

Our code was not helping the model. It was making the decision before the model ever saw the question.

The result was absurd: more code, less capability.

We stopped patching on the spot

After that audit, we immediately froze the batch of fixes that would have added a few more rules.

That same day, we wrote a new direction into the project plan. We would stop patching the system that tried to guess what the user meant before the AI saw the question. The design goal was now to let the AI understand the request and choose its tools. The app would present the process and results clearly while enforcing permissions, privacy, and boundaries around outside actions. Each user would eventually have an isolated runtime so their data and permissions could not mix.

We shelved the scattered patches and reorganized the work around the new direction.

I do not want to make the story prettier than it was. What we completed that day was stopping the old direction, choosing a new one, and putting it into the plan. The new architecture was not built yet, and we had not shown that it could fix the three problems from the beginning of this story.

Guardrails still matter. User data must stay isolated. Location and private information require permission. Actions such as sending an email or placing an order need confirmation. Claims from the AI should be traceable to a source.

But after that day, whenever we want to add one more rule, I will probably ask one question first:

Is this rule protecting the user, or is it just trying to answer before the model can?
